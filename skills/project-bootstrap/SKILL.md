# Project bootstrap

Set up the requested project in its chosen directory. Respect existing project instructions, user choices, and higher-priority rules. Do not overwrite existing files or alter unrelated work.

1. Check whether the directory exists, what it contains, and whether `git rev-parse --show-toplevel` identifies an enclosing repository. Preserve existing repositories, remotes, history, and uncommitted changes. Do not initialize a nested repository without explicit authorization.
2. If a workspace's `GLOBAL.md` or project memory template exists, follow its applicable instructions. Otherwise use the five files in `assets/memory` as a portable starting point. For a new project, place `AGENTS.md` at the project root for agent discovery and place `STATE.md`, `TODO.md`, `DECISIONS.md`, and `HISTORY.md` in `memory/`. Update `AGENTS.md` to refer to those paths and tailor it to the project's safety boundaries. Copy only missing files; preserve existing projects' memory layouts and references instead of creating duplicate records or moving files unless requested. Replace placeholders with verified facts or clearly empty sections. Do not invent architecture, decisions, or completed work. Refer to a global protocol only if it actually exists at the target location.
3. Organize the project so related materials have clear homes and the root stays easy to navigate. Inspect existing conventions and choose only folders useful for this project, such as `docs/` for documentation, `assets/` or `references/` for source materials, `src/` for code, and `outputs/` for deliverables. Keep files that tools expect at the root there. Create folders when needed, not as empty boilerplate. Preserve existing structure and do not move ambiguous or externally referenced files without checking their use; when moving files, update affected paths and verify references. Do not overwrite or delete existing files. Report any files left in place because their intended location or dependencies are unclear.
4. If the project is not already in a repository, run `git init` in the project root. Prepare a `.gitignore` appropriate to the actual stack and sensitive data before staging. Never weaken an existing ignore file or assume it catches every secret.
5. Inspect candidate files and staged diff for credentials, protected configuration, runtime data, generated files, and unrelated work. In an existing nonempty directory, stage only files explicitly verified safe; do not automatically stage unknown files. Create an initial commit when there are verified safe changes and Git identity is configured. If not, report what is needed; never invent an identity. Preserve any existing staged changes and do not include them in a bootstrap commit without authorization.
6. Do not create a remote, change visibility, or push to an unknown or public remote without explicit authorization. A local commit is not an off-machine backup. Report the folder structure, what was initialized, committed, and left pending.
